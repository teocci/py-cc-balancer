# I-15 — Sub-daily (1m/5m/15m) support + Binance REST klines fallback fetcher

- **Improvement ID:** I-15
- **Version:** 0.5.0
- **Date:** 2026-07-18
- **Status:** ✅ DONE (526 tests; live-verified).
- **Related work:** P-17, P-18

## Objective

Add a Binance REST klines fallback fetcher (stores/history_fetch.py, adapted from the prototype script, constants centralized) for deep 1m/5m backfill where ccxt pagination is impractical, and wire sub-daily timeframes into the engine (decision vs fill-resolution timeframe alignment). Network stays in the stores layer.

## Approach

- New `stores/history_fetch.py` — a Binance REST klines fetcher adapted from the prototype script:
  paginated 1000/call against `https://api.binance.com/api/v3/klines`, closed-candles-only,
  exponential backoff on 429/418, gap-aware manifest, HTTP-451 → `data.binance.vision` archive note.
  Constants (`BINANCE_KLINES_URL`, limit, retry codes, the `{'1m','5m'}` LTF set) live in
  `constants.py` per rules 04/14. Stays in the stores layer (managers never do network).
- Fetch selection is per timeframe: 1m/5m → this fallback; 1h/4h/1d → ccxt `fetch_ohlcv_range`
  (I-12). Both normalize to `[t,o,h,l,c,v]` and write to the same append-only sim store.
- Engine: multi-timeframe alignment — the decision timeframe sets rebalance cadence; a finer timeframe
  resolves fills within the decision interval. Handle the sub-daily volume (one-time cached backfill).
- Tests: fallback fetcher paginates/normalizes/handles gaps against a stubbed HTTP layer (no live
  network); per-timeframe routing picks the right source; alignment resolves fills on the finer bars.

## Notes / known limitations

- **15m routing:** 15m is now a *default* fetched timeframe but stays on the **ccxt pager** (its
  volume paginates comfortably); only 1m/5m route to the REST fallback (`SIM_LTF_TIMEFRAMES`).
- **Cross-venue provenance:** the Binance REST fallback always sources from Binance, even when
  `data_exchange` is another venue. Sub-daily LTF candles are then stored under that venue's key and
  the manifest's single `source_endpoint` still names the ccxt venue. This is an accepted
  approximation for a backtest tool (see I-16's false-confidence limits); deep 1m/5m history is
  practically Binance-first. Set `data_exchange = binance` to keep provenance consistent.
