# F-3 — `auth login` collects the OKX passphrase from flags/env, not just interactively

- **Fix ID:** F-3
- **Version:** unreleased (post-0.1.1)
- **Related phase:** Auth

## Symptom

`auth login --exchange okx --key <K> --secret <S>` with valid **live** OKX
credentials fails: the profile saves, but the credential check exits `3`
(`EXCHANGE_ERROR`) and `auth status` reports `credentials: invalid`. The same
keys are valid on OKX. Two independent defects fire on this one command.

## Root cause

### 1. The passphrase is silently never collected (primary bug)

OKX requires a third credential on **every** private request — the
`OK-ACCESS-PASSPHRASE` header, i.e. the passphrase set at API-key creation (see
OKX v5 docs, *REST Authentication*). It is distinct from the web-UI passphrase
that unmasks the secret; key + secret alone can never authenticate to OKX.
ccxt exposes this via `okx().requiredCredentials['password'] == True`, and
`ExchangeStore` already forwards it as the ccxt `password` field.

But `_collect_credentials` returned before ever asking for it:

```python
password = args.passphrase
if key and secret:                       # OKX with --key/--secret short-circuits here
    return key, secret, password         # -> password is None
...
if password is None and requires_passphrase(exchange):
    password = getpass.getpass('Passphrase: ')   # unreachable on the flag/env path
```

So `--key`/`--secret` (or `--from-env`) on OKX saved `password=None`, ccxt sent
an empty passphrase, and OKX rejected the request. The interactive path (no
flags) prompted correctly — the bug only bit the documented non-interactive
route. There was also **no `CCB_PASSPHRASE` env var at all**, so the
no-profile/CI path could never supply a passphrase.

### 2. Live keys checked against the OKX demo endpoint

`DEFAULT_TESTNET = True`, so a bare `auth login` (no `--no-testnet`, no
`CCB_TESTNET`, no TOML) saves a testnet profile and verifies against OKX demo.
Per the ccxt manual, *"sandbox keys are not interchangeable with production
keys"*, so live keys are rejected — and the failure was indistinguishable from
"your keys are bad". This is the same trap class as [F-2](F-2.md); the safety
default is intentional, but the failure is now explained rather than silent.

## Fix

- `_collect_credentials` resolves the passphrase independently of key/secret: a
  `needs_password` gate short-circuits only when no passphrase is required, so a
  complete key+secret pair for OKX still prompts (tty) or errors (non-tty).
- New `CCB_PASSPHRASE` env var (in `constants.py`), imported by `--from-env` and
  by the no-profile config path; masked in all output like the other secrets.
- `_non_interactive_error` names the actual gap — "requires a passphrase; pass
  `--passphrase` (or set `CCB_PASSPHRASE` with `--from-env`)".
- `require_credentials` now fails fast locally when a required passphrase is
  missing, instead of deferring to a cryptic exchange-side error.
- A failed login check prints hint lines explaining the likely cause
  (`profile targets testnet; live keys need --no-testnet`; `<exchange> requires
  --passphrase`). The `--json` payload is unchanged.

## Verification

- Full suite green (402 tests; +9).
- Driven end-to-end (file backend, isolated home):
  - OKX key+secret without passphrase → `okx requires a passphrase; pass
    --passphrase (or set CCB_PASSPHRASE with --from-env)`, exit 2.
  - Bybit key+secret (no passphrase) → saved, unaffected.
  - OKX `--from-env` with `CCB_API_KEY`/`CCB_API_SECRET`/`CCB_PASSPHRASE` →
    saved (previously impossible).
  - `auth list --json` → passphrase masked (`***`), plaintext never leaks.
- **Live OKX key still to confirm:** a `verified` login and `auth status →
  valid` against a real live OKX key (`--no-testnet` + `--passphrase`) — this
  closes the open item in `docs/phases/phase-auth.md`. Unit + offline drives
  prove the credential *plumbing*; only a live key proves OKX acceptance.
